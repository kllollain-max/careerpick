# 클린아이 원고·맞춤 알림 연결

홈페이지에 연결된 `cleaneye.json`을 Threads 원고 입력과 기존 맞춤 웹푸시의 후보 처리에 연결한다. 실제 게시 횟수와 발송 한도는 기존 운영 계약을 따른다.

## 출처와 접수 상태

공용 `cleaneye_source_adapter.py`는 검증된 출처, 24시간 이내 수집 시각, 공고 고유번호와 공식 URL, 기관·제목, 실제 접수기간, 원문 모집 상태를 함께 확인한다. 빈 목록·중복 ID·미래 수집 시각·원문 누락·확인 대기·시험 또는 결과 안내는 발송 후보로 인정하지 않는다. 짧은 제목에 ‘채용’이 없더라도 원문의 고용형태·직무·채용 목적이 확인되면 검토할 수 있다.

`PUB_DATE`와 `PUB_END_DATE`는 이 API의 실제 접수 시작과 마감이다. 날짜만 제공된 마감의 내부 정렬용 `23:59:59`를 실제 마감 시각으로 표시하지 않는다. 시작 또는 마감 당일에 시각이 불분명하면 자동 발송 대상으로 삼지 않는다.

`sourceRegion`과 기관 주소는 기관 소재지다. 실제 근무지 `WORK_PLACE`가 없으면 `region`은 빈 값으로 보존한다. 지역·학력 조건을 알 수 없는 공고는 해당 맞춤 조건과 일치한다고 추정하지 않는다. 고용형태 별칭은 `일반정규직 → 정규직`, `일반계약직/전문계약직 → 계약직`만 추가하며, 원문 표시와 공고 ID는 유지한다.

2026-11-07 13:27:15 KST 운영 스냅샷 351건을 검토했을 때 접수 확인 후보는 265건이었다. 나머지는 접수 예정·확인 대기 등이며 필기시험 안내 1건도 포함한다. 이 수치는 원고 검토 가능 범위이며 실제 원고 작성·발송·기기 수신 건수가 아니다.

## 신규 알림 기준과 보존

기존 ALIO 기준 목록에는 `initialized_sources`가 없을 수 있다. 첫 유효 클린아이 스냅샷에서는 현재 공고 ID 전체를 독립적으로 기준 목록에 저장하고 과거 공고를 신규 알림으로 넣지 않는다. 같은 회차의 새 ALIO 공고는 정상 처리한다. 이후 보지 못했던 적격 클린아이 공고만 신규 후보로 처리한다.

출처가 누락되거나 오래되거나 검증에 실패하면 클린아이 기준 목록을 초기화하거나 지우지 않는다. 제거 후 재등장한 ID도 다시 신규 알림이 되지 않는다. 후보 저장과 재조회 검증이 끝나기 전에는 기준 목록을 전진시키지 않는다.

대기 후보의 최신 접수기간을 먼저 반영한 뒤 보존·마감 검사를 한다. 최신 스냅샷에 있다는 이유만으로 새 ID를 대기 목록에 추가하지 않으며, 기존 `first_seen`, 7일 보존 규칙, 진행 중 작업의 보존, 구독자별 영구 중복 방지를 유지한다.

## 웹푸시

전송 직전에 기존 ALIO 원문 검사 또는 클린아이 공식 API 검사를 적용한다. 클린아이는 기존 승인 키와 검증된 클라이언트로 공식 시도 코드를 조회하고 해당 기관 지역의 전체 응답에서 공고 ID를 찾는다. 현재 원문과 후보의 제목·기관·접수기간·고용형태·근무지 등 매칭에 사용한 필드를 대조한다. 불명확한 응답이나 변경된 원문은 전송을 보류한다.

구독 동의·구독 ID·맞춤 태그는 전송 직전에 다시 확인한다. 영구 큐 소유권과 발송 원장의 예약을 확보한 후에만 OneSignal을 호출한다. 기존 회당 최대 3건, 구독 조회 한도, 불확실한 요청의 자동 재전송 금지를 유지한다. 안정적인 UUID `idempotency_key`를 추가하되 장기 중복 방지는 기존 비공개 원장이 계속 담당한다.

알림 링크는 ALIO의 기존 공고 페이지와 클린아이의 `/#job=cleaneye-번호` 상세 화면을 사용한다. 외부 데이터가 제공한 임의 URL을 알림 목적지로 사용하지 않는다.

## Threads

`threads_writer_input.py --limit 24`는 ALIO와 클린아이를 한 후보 목록에 넣고 기존 5~20일 마감 범위, 정규직 우선·인원순 정렬, 이력 제외와 전체 상한을 적용한다. 클린아이 항목에는 `source`, `official_id`, 원문 지문과 기관지역·근무지를 구분한 `source_context`를 제공한다.

큐 검증과 게시 직전 재검증은 같은 출처 계약을 사용한다. 기존 마스터 프롬프트·CTA·하루 4회·형식 분담·이미지 교대는 유지한다. 근무지 등 필요한 사실이 빠져 있으면 공식 공고·첨부의 실제 근거를 확인해야 한다. 단순히 자료를 읽었거나 후보가 존재한다는 이유로 ready 원고나 실제 게시로 기록하지 않는다.

## 중단된 푸시의 운영자 진단과 복구

`CareerPick targeted job push`의 수동 실행은 두 발송 가드를 `0`으로 설정한다. 기본 `check`와 기존 정기 실행 조건은 유지한다.

1. `diagnose`는 비공개 저장 상태, OneSignal export 요청·다운로드 및 최대 1개 구독 조회를 읽기 전용으로 확인한다. 단계·허용된 오류 코드·집계만 기록한다. 성공해도 차단을 해제하지 않는다.
2. 실패 단계를 확인하고 필요한 코드나 설정을 수정한다. 인증·권한·비용이 필요한 외부 문제는 재시도로 숨기지 않는다. 실제 발송 여부를 알 수 없는 이력을 삭제하거나 재전송하지 않는다.
3. 원인을 검토한 뒤 `resume_after_review`를 별도로 선택하고 정확한 현재 control blob SHA와 짧은 검토 근거를 제공한다. 이 경로는 blocked 상태, 미해결 ledger pending 0, queue reserved/uncertain 0 및 현재 진단 성공을 요구한다.
4. 진단 후 상태를 다시 읽고 기존 `circuit.resume()`의 조건부 갱신으로만 ready 전환을 수행한다. 후보·기준 목록·큐·원장·커서는 초기화하지 않는다. 이 수동 실행도 발송은 0건이다.
5. 다음 자연 예약 실행에서 실제 동작을 확인한다. 수동 진단 성공, 운영 경로 성공, OneSignal 접수, 기기 수신은 각각 구분한다.
