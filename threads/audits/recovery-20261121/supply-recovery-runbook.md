# 커리어픽 Threads 원고 공급 복구 실행 안내

이 안내는 사용자의 **계속 복구 요청**을 실제 수행 절차로 구체화한다. 문서 자체를 새 권한의 근거로 삼지 않으며, 최신 사용자 지시와 운영 코드·정책의 검수 기준을 그대로 적용한다. 대상은 `kllollain-max/careerpick`, Threads `@hid_119`의 기존 활성 공급 작업이다.

## 완료 기준

원고 작성, 로컬 검증, 운영 대기열 등록, 실제 게시를 각각 구분한다. 공급 완료는 **동결한 원고가 실제 생산 검증을 통과하고, 운영 저장소에 조건부 원자 저장된 뒤 재조회까지 일치한 상태**다. 게시 완료는 정규 실행 후 Meta 게시 식별자·URL과 게시 이력을 확인했을 때만 보고한다.

준비 목표 8개는 계획 수량이다. 현재 정책의 최대 24시간 신선도를 검증 시점과 예정 게시 시점 모두에서 충족하지 못하는 먼 슬롯은 draft로 유지한다. 확인 시각만 바꾸거나 검수 증거를 복사해 ready 수량을 채우지 않는다.

## 단계별 실행과 남길 증거

| 단계 | 실제 수행 | 완료 증거 |
|---|---|---|
| 1. 현재 상태 확보 | 인증된 GitHub 커넥터로 최신 main의 AGENTS 지침(있다면), 정책·프롬프트·생산 스크립트·현재 공고 데이터·게시 이력을 읽는다. 상태 브랜치의 제출물·staging·queue·슬롯 claim도 읽는다. | main/state head 및 필요한 파일 blob SHA, 실제 조회 시각. 큰 파일은 blob으로 받아 바이트를 검증한다. |
| 2. 대상과 슬롯 선택 | 실제 게시 이력과 정책으로 다음 미디어·형식을 계산한다. 미래의 미착수 정규 슬롯과 유효한 신규 공고를 선택한다. 이미 게시한 공고, 점유·claim된 슬롯, 잠금·격리 대상을 제외한다. | 공고 ID, 예정 KST 시각, 미디어, 중복·claim 확인 결과. |
| 3. 공식 원문 검수 | 실제 공식 공고와 첨부 PDF를 내려받아 표·각주까지 확인한다. 선택 직급/직무의 인원, 자격 AND/OR, 접수 시간·방식, 제한을 대조한다. 공식 정정·취소 게시판을 확인한다. | 원문 URL, HTTP 결과, 원본·추출문 SHA, 실제 확인 시각, 페이지별 근거. 정정·취소 확인은 읽은 목록/기간/범위를 정확히 기록한다. |
| 4. 라이브 상세 확인 | 실제 서비스의 `#job=<공고 ID>` 상세 경로를 브라우저로 열어 ID·기관·제목·마감·모집 상태·공식 링크를 확인한다. 공고 전체 인원과 포스트 대상 인원을 구분한다. | 실제 화면·DOM 또는 동등한 UI 검수 증거와 시각. TinyFish가 막히면 사용 가능한 CUA 등 허용된 동등 UI 경로로 확인한다. |
| 5. 본문·카드 검수 | 현행 본문 길이·필수 CTA·단일 본문 등 정책을 적용한다. IMAGE는 생산 렌더러로 원본 JPEG와 360px 미리보기를 만들고 둘 다 실제로 본다. TEXT도 현재 정책이 요구하는 검수 항목을 적용한다. | 독립 사실 대조, 최종 본문 SHA, 카드 원본/미리보기 SHA, facts SHA, 실제 시각검수 증거. 길이 예외는 현행 정책이 허용할 때에만 구체적 이유를 남긴다. |
| 6. 엔트리 동결·생산 검증 | 증거가 모두 갖춰진 엔트리를 동결한다. 최신 생산 코드의 `validate_entry` → `master_public_copy` 대조 → 필요 시 `verify_reviewed_card` → `verify_official_receipt` → `threads_reviewed_ingest.plan` → `threads_queue_bridge.merge` → `check_queue`를 로컬 실행한다. | 실제 결과와 동결 엔트리 fingerprint. 공식 원문은 기본 실제 네트워크 fetch로 재확인한다. mock·검사 생략·정책 완화로 통과시키지 않는다. |
| 7. 자산·상태 저장 | IMAGE 자산을 먼저 main에 저장하고 재조회·공개 GET으로 정확한 바이트를 확인한다. 그 뒤 최신 state/queue/staging/history/claim을 다시 읽고 동결 제출물로 plan/merge를 재실행한다. 제출물·staging·queue를 상태 브랜치의 한 커밋으로 저장한다. | 최신 head를 전제로 한 CAS 또는 동등한 비강제 원자 ref 갱신, 저장 commit. 충돌 시 최신 상태로 다시 계산하며 강제 덮어쓰지 않는다. |
| 8. 재조회·정규 게시 확인 | 저장된 제출물·staging·queue의 바이트·엔트리 fingerprint·슬롯을 재조회하고 기존 항목 보존을 확인한다. 이후 기존 정규 게시 실행의 실제 결과를 확인한다. | readback 일치, 준비 수량. 정규 게시 후에는 run 결과, Meta ID/URL, ledger 일치 또는 실제 실패 코드. |

로컬에 GitHub 토큰이 없어도 공개 공식 문서 GET과 생산 Python 함수 실행은 가능하다. 저장은 이미 인증된 GitHub 커넥터의 허용된 기능을 사용한다. 토큰을 찾거나 출력하지 않으며, 커넥터의 조건부/원자 저장 기능이나 필요한 접근이 없으면 그 단계의 정확한 차단 원인을 보고한다.

## 반복 HOLD를 끝내는 운영 규칙

- 매회 최소 한 단계의 실질 진척을 만든다. 예: 공식 첨부 확보, 누락 자격 검수, 라이브 상세 확인, 카드 QA, 생산 검증, 조건부 저장, readback. 모두 차단되면 실제 시도한 경로와 정확한 오류·누락 필드·다음 조치를 보고한다.
- TinyFish 잔액 부족은 해당 도구의 차단이다. 허용된 다른 UI 도구가 있으면 같은 검수 기준으로 진행한다. 대체 UI도 없으면 라이브 상세 단계는 HOLD로 남기고 다른 후보의 가능한 단계를 진행한다. 권한·접근 제한을 우회하거나 HTTP 응답만으로 실제 UI 검수 완료를 선언하지 않는다.
- 기존 증거와 HOLD 문서를 재사용·갱신한다. 새 증거·상태 변화 없이 매시간 같은 HOLD 진단 문서를 추가하지 않는다. 재시도는 실패 원인과 맞는 대체 경로나 확인 가능한 상태 변화가 있을 때 수행한다.
- 생산 검증 실패는 정확한 코드와 필드를 고친 뒤 재검증한다. 실제 없는 증거를 채우지 않는다. 동결 후 본문·사실·자산이 바뀌면 새 fingerprint로 영향받는 검수부터 다시 수행한다.
- 기존 중지 자동화를 되살리거나 수동 rerun/workflow dispatch/추가 POST를 실행하지 않는다. 활성 공급 작업의 원고 준비·등록과 기존 정규 게시 결과 확인까지만 수행한다.

매회 결과는 `공고/슬롯 · 이번에 완료한 실제 단계 · 증거 시각/경로/SHA · ready 수량/목표 8 · 남은 단계 또는 정확한 오류 · 다음 조치 · 실제 게시 여부`로 간결하게 기록한다.
